# Report Fetcher — скачивание и трансформация отчётов Zoomos (спек 1 из 3)

## Контекст

В сервисе export.zoomos.by отчёты формируются длинными GET-запросами (URL с десятками
query-параметров, включая `cols=` для управления набором/порядком/именами колонок на
стороне Zoomos). Формирование некоторых отчётов занимает от минут до часа и более — GET-запрос
всё это время просто держит открытое соединение.

Нужен универсальный инструмент: скачать такой отчёт в фоне, дополнительно преобразовать
данные (то, что Zoomos сам сделать не может — вычисляемые колонки, подстановка значений
из внешнего справочника), собрать итоговый файл с нужным набором/порядком/именами колонок
и сохранить результат для скачивания.

Это первый из трёх независимых спеков одной задачи:
1. **Report Fetcher** (этот документ) — скачивание + трансформация + сохранение файла.
2. Отправка готового файла по почте выбранным адресатам (отдельный спек).
3. Расписание автозапуска конфигов (отдельный спек).

Email и расписание сознательно вынесены за рамки — у них своя специфика (SMTP-интеграция,
которой в проекте пока нет вообще; cron-инфраструктура). Каждый спек добавляется поверх
результата этого без изменения его архитектуры.

## Цель / вне рамок

**Цель спека 1:** пользователь создаёт переиспользуемый конфиг отчёта (URL + правила
трансформации), запускает его вручную из UI, видит live-статус длинного скачивания и в
конце скачивает готовый файл.

**Вне рамок:** отправка почты, расписание/cron, автоопределение параметров URL через
конструктор (URL хранится и вводится одной строкой), поддержка форматов справочника кроме
Excel/CSV, многопользовательские права доступа к конфигам.

## Модель данных

### `ReportConfig`

Переиспользуемая настройка отчёта.

| Поле | Тип | Описание |
|---|---|---|
| `id` | Long | PK |
| `name` | String | Название конфига |
| `clientId` | Long, nullable | FK на `Client` — необязательная привязка отчёта к клиенту, для организации/фильтрации в списке конфигов |
| `sourceUrl` | Text | Полный URL запроса к export.zoomos.by, как есть, одной строкой |
| `lookupFileOriginalName` | String, nullable | Имя загруженного файла-справочника |
| `lookupFileStoredPath` | String, nullable | Путь к сохранённому файлу-справочнику на диске |
| `lookupFileFormat` | String, nullable | `CSV` / `XLSX` / `XLS`, определяется по расширению при загрузке |
| `lookupFileDelimiter` | String, nullable | Разделитель для CSV-справочника (по умолчанию `;`) |
| `lookupFileEncoding` | String, nullable | Кодировка для CSV-справочника (по умолчанию `UTF-8`) |
| `detectedReportColumns` | Text (JSON-массив строк), nullable | Заголовки, реально пришедшие в последнем успешном скачивании; заполняется автоматически, используется билдером `outputColumns` для выпадающих списков |
| `outputFormat` | String | `xlsx` / `csv`, по умолчанию — формат исходного отчёта |
| `rowFilterExpression` | Text, nullable | Необязательное булево SpEL-выражение — строки, для которых оно возвращает `false`, не попадают в итоговый файл. Вычисляется после `COMPUTED`/`LOOKUP`, см. раздел «Фильтрация строк» |
| `createdAt` / `updatedAt` | Timestamp | |

### `ReportOutputColumn` (дочерняя таблица `ReportConfig`, 1:N)

Единый упорядоченный список колонок итогового файла. Каждая запись — это одна выходная
колонка одного из трёх типов.

| Поле | Тип | Описание |
|---|---|---|
| `id` | Long | PK |
| `configId` | Long | FK на `ReportConfig` |
| `type` | Enum | `SOURCE` \| `COMPUTED` \| `LOOKUP` |
| `outputHeaderName` | String | Итоговый заголовок колонки в файле (переименовываемый) |
| `position` | Integer | Порядок в итоговом файле |
| `included` | Boolean | Включать ли колонку в итоговый файл |
| `sourceColumnName` | String, nullable | Для `SOURCE` — имя колонки в скачанном отчёте |
| `formula` | Text, nullable | Для `COMPUTED` — выражение Spring SpEL, например `['Цена'] - ['РРЦ']` |
| `keyColumnInReport` | String, nullable | Для `LOOKUP` — имя колонки в отчёте, по которой ищем |
| `keyColumnInLookup` | String, nullable | Для `LOOKUP` — колонка-ключ в файле-справочнике |
| `valueColumnInLookup` | String, nullable | Для `LOOKUP` — колонка-значение в файле-справочнике |

### `ReportRun`

История запусков конфига.

| Поле | Тип | Описание |
|---|---|---|
| `id` | Long | PK |
| `configId` | Long | FK на `ReportConfig` |
| `status` | Enum | `PENDING` → `DOWNLOADING` → `TRANSFORMING` → `DONE` / `ERROR` |
| `startedAt` / `finishedAt` | Timestamp | |
| `errorMessage` | Text, nullable | Причина ошибки для `ERROR` |
| `resultFilePath` | String, nullable | Путь к готовому файлу на диске для `DONE` |
| `triggeredBy` | Enum | `MANUAL` (единственное значение в этом спеке; задел под будущий `SCHEDULE`) |

### `ZoomosAuthSession`

Хранит сессионные куки для авторизации на export.zoomos.by. Одна строка на всё приложение
(аналог удалённой ранее вместе с Zoomos Check таблицы `zoomos_sessions` — та же идея, новая
Flyway-миграция, так как исходная таблица была дропнута).

| Поле | Тип | Описание |
|---|---|---|
| `id` | Long | PK |
| `cookies` | Text (JSON) | Сериализованный список кук (`name`, `value`, `domain`, `path`, `expires` и т.д.) |
| `updatedAt` | Timestamp | Обновляется при каждом сохранении новых кук |

## Авторизация и куки

export.zoomos.by требует авторизованную сессию для скачивания отчёта. Раньше в проекте уже
была аналогичная механика (через Playwright, до удаления Zoomos Check) — логин формой
(`j_username`/`j_password` на `{zoomos.base-url}/login`), куки из БД. Переиспользуем тот же
принцип, но без браузера — на чистом `java.net.http.HttpClient` с `CookieManager`.

Креды берутся из уже существующих в `application.properties` свойств `zoomos.username` /
`zoomos.password` (не удалялись вместе с Zoomos Check) — новый источник конфигурации не нужен.

**Поток проверки/обновления сессии** (часть этапа `DOWNLOADING`, выполняется перед фактическим
скачиванием отчёта на каждый `ReportRun`):

1. Собрать `HttpClient` с `CookieManager`; загрузить в его `CookieStore` куки из
   `ZoomosAuthSession` (если запись есть).
2. Выполнить GET к `sourceUrl`.
3. Если итоговый URL ответа (после редиректов) содержит `/login` — сессия протухла или её не
   было. Выполнить логин: `POST {zoomos.base-url}/login` с полями `j_username`/`j_password` из
   конфига, проверить, что после логина редиректа на `/login` больше нет. Сохранить обновлённые
   куки в `ZoomosAuthSession`. Повторить исходный GET-запрос к `sourceUrl` ещё раз (один повтор).
4. Если и после логина результат снова ведёт на `/login` — авторизация не удалась:
   `ReportRun.status = ERROR`, сообщение «Авторизация не удалась — проверьте логин/пароль в
   настройках zoomos.*».
5. Если исходный GET сразу успешен (куки были рабочими) — куки в `ZoomosAuthSession` всё равно
   обновляются из ответа (сервер может ротировать сессионный токен по ходу).

Так авторизация выполняется реактивно — по факту неудачного запроса, без отдельного
«прогревочного» запроса перед каждым запуском.

## Скачивание (fetch flow)

- Запуск — кнопка «Запустить» на странице конфига. Создаётся `ReportRun` со статусом
  `PENDING`, дальше обработка полностью асинхронна.
- Выполняется в выделенном `@Async` executor'е (`reportFetchExecutor`, пул 2–3 потока —
  несколько отчётов могут тянуться параллельно, но не десятками).
- HTTP-клиент — `java.net.http.HttpClient` с большим таймаутом чтения (например, 3 часа),
  так как соединение просто долго висит, пока Zoomos формирует файл.
- Повторный запуск того же конфига, пока предыдущий ещё не завершён (`PENDING`/`DOWNLOADING`/
  `TRANSFORMING`), блокируется на уровне API — нельзя запустить второй раз поверх первого.
- Статус меняется по ходу: `PENDING` → `DOWNLOADING` (начало запроса) → `TRANSFORMING`
  (байты получены, идёт парсинг/трансформация) → `DONE` (файл сгенерирован) либо `ERROR`
  на любом этапе.
- Каждое изменение статуса пишется в `ReportRun` (источник истины) и пушится через
  существующий WebSocket-канал — по аналогии с прогрессом импорта/экспорта. Если страница
  закрыта/обновлена, актуальный статус читается из БД при загрузке.

## Трансформация данных

1. **Парсинг скачанного отчёта.** Скачанные байты сохраняются во временный файл, формат
   (`xls`/`xlsx`/`csv`) определяется по `Content-Type` ответа или расширению в `sourceUrl`
   (например, `/convert/xls`). Файл оборачивается во временный `FileMetadata` и читается
   через существующий `fileReaderUtils.readAllRows(...)` — без дублирования кода чтения.
2. **Определение колонок.** После успешного чтения заголовок отчёта сохраняется в
   `ReportConfig.detectedReportColumns` (перезаписывается при каждом успешном ране).
3. **Вычисляемые колонки (`COMPUTED`).** Каждая строка отчёта превращается в
   `Map<String, Object>` (ключ — заголовок колонки). `formula` — выражение Spring SpEL,
   вычисляется через `SimpleEvaluationContext` с этим Map как root-объектом (в classpath уже
   есть `spring-expression`, новая зависимость не нужна). Ошибка вычисления в одной строке
   → пустая ячейка + WARN в лог рана, весь прогон не прерывается.
4. **Lookup-колонки (`LOOKUP`).** Файл-справочник (`lookupFileStoredPath` конфига) читается один
   раз через `fileReaderUtils.readAllRows(...)` (тоже через временный, не персистентный
   `FileMetadata`) и индексируется в `Map<String key, List<String> row>` по `keyColumnInLookup`.
   Для каждой строки отчёта берётся значение `keyColumnInReport`, ищется в индексе, подтягивается
   `valueColumnInLookup`. Не найдено → пустая ячейка. Подход аналогичен уже существующему
   `DataMergerService`, но не переиспользует его код напрямую (другая DTO-модель).

   Ограничение MVP: все `LOOKUP`-колонки одного конфига используют один и тот же
   `keyColumnInLookup` (один файл-справочник — один ключ индексации). Это проверяется при
   сохранении конфига.

   **Пример.** В отчёте есть колонка `ОГРН`, в справочнике — тоже `ОГРН` плюс поля `Юр. лицо`,
   `Город`, `Статус`. Чтобы подтянуть все три поля отдельными колонками, заводится **по одной
   `LOOKUP`-записи `ReportOutputColumn` на каждое поле**, все с одинаковыми
   `keyColumnInReport = ОГРН` / `keyColumnInLookup = ОГРН`, но разным `valueColumnInLookup`:

   | type | outputHeaderName | keyColumnInReport | keyColumnInLookup | valueColumnInLookup |
   |---|---|---|---|---|
   | LOOKUP | Юр. лицо | ОГРН | ОГРН | Юр. лицо |
   | LOOKUP | Город юр. лица | ОГРН | ОГРН | Город |
   | LOOKUP | Статус контрагента | ОГРН | ОГРН | Статус |

   Один справочник → сколько угодно выходных колонок. Найден ОГРН — все три ячейки
   заполняются из одной строки справочника; не найден — все три пустые, остальные колонки
   строки не затрагиваются.
5. **Фильтрация строк.** Если у конфига задан `rowFilterExpression`, он вычисляется для
   каждой строки **после** того, как посчитаны `COMPUTED`- и `LOOKUP`-значения (то есть можно
   фильтровать и по подтянутым из справочника полям). Выражение должно вернуть `true`/`false`
   через `SimpleEvaluationContext` с тем же `Map<String, Object>` строки, что и формулы.
   Строки, где выражение вернуло `false`, в итоговый файл не попадают. Пустое поле — фильтрации
   нет, идут все строки. Ошибка вычисления выражения на конкретной строке трактуется как
   `false` (строка исключается) + WARN в лог рана.
6. **Сборка итогового файла.** Для каждой включённой (`included = true`) записи
   `ReportOutputColumn`, упорядоченной по `position`, формируется значение (из отчёта,
   вычисленное или lookup) под заголовком `outputHeaderName`. Генерация — через
   `FileGeneratorService.generateFile(...)` с `ExportTemplate`, формат — `outputFormat`
   конфига. Файл сохраняется во временную папку отчётов, путь — в `ReportRun.resultFilePath`.

## UI / API

### Страницы (`/utils/report-fetcher`)

- **Список конфигов** — имя, клиент (если привязан) с возможностью фильтрации по клиенту,
  дата/статус последнего запуска, кнопки «Запустить» / «Редактировать» / «История».
- **Создание/редактирование конфига** — имя, необязательный выбор клиента (`clientId`),
  `sourceUrl` (textarea), загрузка/замена файла-
  справочника, поле `rowFilterExpression` (текстовое, необязательное, с той же справкой по
  SpEL, что и у формул — см. раздел «Справка по SpEL для пользователя»), редактор
  `outputColumns`:
  - список карточек/строк, перетаскиваемых через SortableJS (тот же паттерн, что уже
    используется в `clients/list.html`) — drag-handle меняет `position`;
  - инлайн-переключатель `included`;
  - текстовое поле `outputHeaderName` (переименование);
  - выбор `type`, при выборе раскрываются свои поля:
    - `SOURCE` → выпадающий список из `detectedReportColumns` (если ещё пусто — свободный
      текст с подсказкой «запустите отчёт хотя бы раз, чтобы получить список колонок»);
    - `COMPUTED` → текстовое поле формулы с автокомплитом имён колонок из
      `detectedReportColumns` и кнопкой-подсказкой «Как писать формулы?» (открывает справку
      по SpEL);
    - `LOOKUP` → выпадающие списки `keyColumnInReport` (из `detectedReportColumns`),
      `keyColumnInLookup`/`valueColumnInLookup` (из заголовка загруженного файла-справочника,
      доступны сразу после загрузки файла, скачивания отчёта ждать не нужно). Кнопка
      «Добавить ещё поле из этого справочника» — клонирует строку с теми же ключами, оставляя
      выбрать только новый `valueColumnInLookup` (ускоряет сценарий «несколько колонок из
      одного lookup»).
- **История запусков конфига** — таблица `ReportRun` (статус, время старта/финиша, ссылка на
  скачивание при `DONE`, текст ошибки при `ERROR`), с live-обновлением текущего статуса через
  WebSocket.

### API

- CRUD для `ReportConfig` (+ вложенные `ReportOutputColumn`)
- `POST /utils/report-fetcher/{configId}/run` — запуск, создаёт `ReportRun`, возвращает `runId`
- `GET /utils/report-fetcher/runs/{runId}` — статус/результат
- `GET /utils/report-fetcher/runs/{runId}/download` — скачать готовый файл

## Справка по SpEL для пользователя

Формулы (`COMPUTED`) и фильтр строк (`rowFilterExpression`) используют один и тот же язык
выражений — Spring Expression Language (SpEL). Пользователю не нужно знать программирование:
достаточно знать пару правил и посмотреть на примеры. Этот текст должен быть доступен прямо в
UI (кнопка/иконка «?» рядом с полем формулы и полем фильтра — раскрывает шпаргалку ниже, без
перехода на отдельную страницу).

**Главное правило:** название колонки всегда пишется в квадратных скобках с кавычками —
`['Название колонки']`, как оно называется в отчёте (или в справочнике для lookup-полей, если
выражение написано после lookup-колонок). Один и тот же синтаксис работает для любых названий,
включая имена с пробелами и знаками препинания — не нужно запоминать, когда скобки обязательны,
а когда нет.

*(Техническая деталь реализации: выражение вычисляется через Spring SpEL с самой строкой отчёта
— `Map<String, Object>`, ключ = заголовок колонки — как корневым объектом (`Expression.getValue(row)`),
поэтому `['Название']` — это обычная индексация Map, работающая "из коробки" без дополнительной
настройки контекста выполнения.)*

### Формулы (числовые/строковые вычисления)

| Что нужно | Как написать | Пояснение |
|---|---|---|
| Разница двух колонок | `['Цена'] - ['РРЦ']` | Обычная арифметика: `+ - * /` |
| Процент отклонения | `(['Цена'] - ['РРЦ']) / ['РРЦ'] * 100` | Скобки работают как в математике |
| Объединить текст из двух колонок | `['Город'] + ', ' + ['Улица']` | `+` для текста — склеивание строк |
| Колонка с пробелом в названии | `['Цена со скидкой'] - ['Цена до скидки']` | Тот же синтаксис, что и для простых названий |
| Округление | не требуется — `FileGeneratorService` сам форматирует числа | Округление формулой обычно не нужно |

### Условия (для фильтра строк, а также внутри формул через `?:`)

| Что нужно | Как написать | Пояснение |
|---|---|---|
| Ячейка не пустая | `['ОГРН'] != null and ['ОГРН'] != ''` | `!=` — «не равно», `null` — «пусто» |
| Ячейка пустая | `['ОГРН'] == null or ['ОГРН'] == ''` | `==` — «равно» |
| Число больше значения | `['Цена'] > 0` | Сравнения: `> < >= <= == !=` |
| Несколько условий одновременно (И) | `['ОГРН'] != null and ['Цена'] > 0` | `and` — оба условия должны быть верны |
| Любое из условий (ИЛИ) | `['Статус'] == 'Активен' or ['Статус'] == 'Новый'` | `or` — достаточно одного условия |
| Отрицание | `not (['Статус'] == 'Удалён')` | `not` — «не» |
| Текст содержит подстроку | `['Название'].contains('Акция')` | `.contains(...)` — проверка вхождения |
| Условное значение («если-то-иначе») в формуле | `['Цена'] > ['РРЦ'] ? 'Дороже' : 'Дешевле или равно'` | Тернарный оператор: `условие ? если_true : если_false` |

### Типичные ошибки

- Название колонки без квадратных скобок (`Цена конкурента` вместо `['Цена конкурента']`) —
  выражение не соберётся, если название содержит пробелы или начинается с цифры.
- Сравнение текста и числа (`['Цена'] == '100'` вместо `['Цена'] == 100`) — не сработает как ожидается.
- Если формула/фильтр написана с ошибкой — конкретная строка получит пустую ячейку (для
  формулы) или будет исключена (для фильтра), весь прогон не остановится; все такие случаи
  видны в логе рана.

## Обработка ошибок

- Таймаут/сеть/HTTP-ошибка при скачивании → `ReportRun.status = ERROR` с понятным сообщением
  (таймаут vs HTTP-код vs пустой ответ).
- Ошибка парсинга (неверный формат, битый файл) → `ERROR` с деталями.
- Ошибка одной формулы/lookup-строки → не валит весь ран: пустая ячейка + WARN в лог,
  финальный статус всё равно `DONE`.
- Попытка запустить конфиг, у которого уже есть активный (`PENDING`/`DOWNLOADING`/
  `TRANSFORMING`) `ReportRun` → отклоняется на уровне API.
- Авторизация не удалась после логина (см. раздел «Авторизация и куки») → `ERROR` с сообщением
  «Авторизация не удалась — проверьте логин/пароль в настройках zoomos.*».

## Тестирование

- Unit-тесты вычисления SpEL-формул (валидные выражения, ошибка в выражении → пустая ячейка,
  не падает весь прогон).
- Unit-тесты lookup-сопоставления (найдено / не найдено / дубликаты ключей в справочнике,
  несколько `LOOKUP`-колонок из одного справочника).
- Unit-тесты `rowFilterExpression` (строка проходит / не проходит фильтр, фильтр по
  вычисленному lookup-полю, ошибка в выражении → строка исключается).
- Unit-тест сборки итогового файла по `outputColumns` (порядок, переименование, исключённые
  колонки).
- Unit-тесты авторизации: куки валидны → логин не вызывается; куки протухли (редирект на
  `/login`) → выполняется логин, куки обновляются, исходный запрос повторяется; логин с
  неверными кредами → `ReportRun.status = ERROR`.
- Интеграционный тест на замоканном HTTP-эндпоинте: полный цикл `PENDING → DOWNLOADING →
  TRANSFORMING → DONE`, включая обновление `detectedReportColumns`.
- Интеграционный тест сценариев ошибок (таймаут, битый ответ, повторный запуск активного рана,
  неудачная авторизация).
